# doc_common: notes for coding agents

This is the guide for every coding agent (Codex, Cursor, Claude and others)
working on DocHelper's shared Rust crates. `CLAUDE.md` imports it, so
Claude Code reads the same rules. The app's own guide is `AGENTS.md` at the
root of the app repository; read it first. Each engine under `packages/`
has its own `AGENTS.md` too.

## What this is

DocHelper is a Flutter app, Android first, whose document engines are
written from scratch in Rust. It is growing from a PDF toolkit into an
all-in-one office app (word processor, spreadsheets, presentations, PDFs)
so the owner's father can do office work on a phone instead of a laptop.

`packages/doc_common` holds the **Rust crates every engine shares**: ZIP,
XML, text encodings, document packages, the FFI plumbing, and for export
and old Office files pictures, fonts, layout, a PDF writer, compound files,
OfficeArt and metafiles.

- **It is Rust only**: no Dart package, no native library of its own. The
  engines link its crates through relative path dependencies
  (`../../../../doc_common/crates/<crate>` from an engine's crate).
- **It lives in the app's tree for now**, not in its own repository. The
  owner's rule is that every package gets its own repository and becomes a
  submodule; for this one that waits until phase 10's waves 1 and 2 have
  landed and the owner has created `koundinyalanka1/doc_common` (PLAN.md
  "Next steps", and "Owner decisions" in `docs/PHASE10_PLAN.md`). Then: `git subtree split
  --prefix=packages/doc_common` into that repository's `main`, and `git
  submodule add` it at the same path. The engines' relative paths keep
  working because the path does not change.
- **The PDF engine (`flutter_pdf_core`) does not use it.** It has its own
  parsers and codecs.

## The owner's rules

These apply here in full; the app's `AGENTS.md` has them all.

- **Everything is Rust, written from scratch.** No C or C++ is written or
  vendored. `extern "C"` on exported Rust functions is only the calling
  convention `dart:ffi` needs.
- **Allowed dependencies** are only these small primitives: `flate2` (raw
  deflate), RustCrypto (`aes`, `cbc`, `sha2`, `md-5`) and `getrandom`,
  `serde`/`serde_json` (only at the FFI boundary, so not in these crates),
  and `thiserror`. Today the crates use only `flate2` and `thiserror`. Do
  not add document, ZIP, XML, image, font, encoding or Office crates.
  Data such as code-page tables and open-licensed fonts is fine.
- **Each crate sets its own dependency versions** (no `workspace = true`),
  so it works as a path dependency from any engine's workspace.
- **Never damage a user's file.** These crates are what makes that true:
  `doc_opc` copies untouched parts raw, `doc_xml` keeps what it does not
  understand, `doc_ffi::save_verified` saves only bytes that read back and
  verify. Keep those properties.
- **Commit or push only when the owner asks.** Work on `main`. A commit
  message is one plain imperative sentence saying what the change does for
  the user, without a type prefix. Changes here are commits in the app
  repository, since this folder is part of it.

## The crates

| Crate | What it does | Used by |
| --- | --- | --- |
| `doc_zip` | ZIP read and write: ZIP64, data descriptors, CP437 and UTF-8 names, checksums, bounded decompression (`ReadLimits`, `ExpansionLimits`), raw copying of unchanged entries | `doc_opc`, `doc_odf`; sheet, word, slide and archive engines |
| `doc_xml` | Pull `Reader`; a round-tripping `Document`/`Element` tree; `XmlWriter`; namespace identities (`ns`, Strict = Transitional OOXML); OOXML `_xHHHH_` strings; never expands DTD entities | `doc_opc`, `doc_odf`; sheet, word, slide |
| `doc_encoding` | UTF-8/16/32 and 32 single-byte code pages, with detection; tables generated by `tools/gen_tables.py` | `doc_xml`; text, sheet, word, slide |
| `doc_opc` | Document packages (OOXML and ODF): parts, relationships, content types, recorded changes; saving copies untouched parts raw and keeps ODF's `mimetype` first; `PackageLimits`, `duplicate_parts()` | sheet, word, slide |
| `doc_odf` | Flat OpenDocument (`.fodt/.fods/.fodp`) to packages (`unflatten`) and back (`flatten`) | sheet, word, slide |
| `doc_ffi` | The FFI plumbing: `FfiError` and codes, `call_i64`/`call_str`/`call_buffer` (panic guards on a 16 MB-stack worker), string and buffer ownership, `Registry` of sessions, `read_file`, `write_file_atomically`, `save_verified`, backups and stale temp files | every engine's `*_ffi` crate except PDF |
| `doc_image` | Picture kinds and sizes; PNG, GIF (first frame) and BMP decoded; JPEG headers for passthrough; PNG written; `MAX_PIXELS` 24M | `doc_metafile`, `doc_pdf`; slide |
| `doc_font` | TrueType/OpenType faces and collections: metrics, cmaps, widths, `kern` and GPOS pair kerning, subsetting, outlines; `FontBook` finds faces, Office substitutes and fallbacks | `doc_layout`, `doc_metafile`, `doc_pdf`; sheet, word, slide |
| `doc_pdf` | A PDF writer for exports: paths, fills, gradients, pictures, Type 0 text with ToUnicode, links; origin top left | `doc_layout`; sheet, word, slide |
| `doc_layout` | Paragraph layout into lines (fallback faces, kerning, breaking, tabs, list labels, alignment, spacing), drawn into `doc_pdf` pages. No glyph shaping yet (Indic, Arabic) | sheet, word, slide |
| `doc_cfb` | OLE2 compound files (`.doc`, `.xls`, `.ppt`, WPS binaries), read only, every chain and reservation checked | sheet, word, slide |
| `doc_art` | OfficeArt records in those files: shapes, properties, stored pictures back to files, under a blip `Budget` | word, slide |
| `doc_metafile` | WMF and EMF drawn into pixels (anti-aliased rasterizer, PNG out) under a render `Budget` (about 4M items) | word, slide |

`README.md` in this folder has the same table in short.

## Building and testing

Start with `export PATH=$HOME/.cargo/bin:$PATH` (on the owner's Mac too:
cargo is not on `PATH` there). Rust 1.88 or newer for these crates
(`slice::as_chunks`); 1.92 or newer for `build_libs.sh host`, which on
Linux also builds the PDF engine.

```bash
cd packages/doc_common
cargo test --release      # every crate; 176 tests passed on 2026-10-18
cargo clippy --release --all-targets -- -D warnings
```

- **Some tests need things from the system** and pass without checking
  anything when they are missing: the font, layout, PDF and metafile
  tests use Carlito and Liberation from `/usr/share/fonts/truetype`
  (Debian packages `fonts-crosextra-carlito`, `fonts-liberation`); the
  PDF writer's tests use `pdftotext` and `pdfinfo` (`poppler-utils`); a
  `doc_zip` memory test uses `prlimit`. Install them before trusting the
  count. They were all present when 176 passed.
- `bash scripts/build_libs.sh test` (from the app root) runs these tests
  in debug first, then every engine's. After changing a crate, run that,
  then `bash scripts/build_libs.sh host`, then the app's tests with
  `eval "$(bash scripts/build_libs.sh env)"`: every engine that uses
  the crate is affected.
- **Android preflight.** `verifyEngines` in `android/app/build.gradle.kts`
  compares each engine binary with the newest source under its own crates
  and anywhere under `doc_common/crates`. A change here makes every
  engine's Android binaries stale: rebuild them with `bash
  scripts/build_libs.sh android` before building an APK. If cargo finds
  nothing to rebuild for an engine that does not use the changed crate,
  `touch` that engine's libraries.
- **Style.** There is no `rustfmt.toml` and the code is hand-formatted to
  about 120 columns. Do not run `cargo fmt` over the workspace; match the
  surrounding style. Doc comments are plain prose.

## Limits these crates enforce (phase 10, wave 1)

Engines are fed hostile files. Allocation aborts and stack overflows cannot
be caught by `catch_unwind`, so every count read from a file is bounded
before it is used. Wave 1 of phase 10 (PLAN.md progress log, 2026-10-17
and 18) set these:

| Limit | Value | Where |
| --- | --- | --- |
| XML nodes in one tree | 2,000,000, then a too-large error | `doc_xml::MAX_NODES` |
| XML nesting | 512 (the deepest real part found was 23); clone, compare and drop are iterative | `doc_xml::MAX_DEPTH` |
| XML part read as a tree | 64 MB | `doc_opc::PackageLimits::max_xml_part` |
| Any part; all parts together | 512 MB and 1 GB (256 MB and 512 MB on 32-bit) | `PackageLimits` |
| ZIP expansion | per entry and in all, with a ratio check past a floor | `doc_zip::ReadLimits`, `ExpansionLimits` |
| Picture size | 24M pixels | `doc_image::MAX_PIXELS` |
| Metafile render | about 4M items (points, edges, dashes, text), and painting of up to 256 times the canvas's pixels (at least 1M) | `doc_metafile::raster::MAX_ITEMS`, `PAINT_LAYERS`, `Budget` |
| Old Office pictures | a decompression budget per import | `doc_art::Budget` |
| Compound files | no reservation larger than the file can fill; checked sector arithmetic | `doc_cfb` |
| Engine call stack | 16 MB worker thread per calling thread | `doc_ffi::CALL_STACK_BYTES` (in `src/stack.rs`) |
| Backups | 500 MB in all | `doc_ffi::BACKUP_CAP_BYTES` (in `src/files.rs`) |

- A too-large part, or a tree over `doc_xml::MAX_NODES`, reaches an
  engine as `OpcError::Zip(ZipError::TooLarge(part))` (`OpcError` has no
  `TooLarge` of its own). Engines should report it as `TOO_LARGE`, not
  `CORRUPT`: word and slide do; sheet (`xlsx/read.rs`, `ods/read.rs`)
  still reports `CORRUPT`, and word turns `doc_xml::XmlError`s it gets
  directly into `CORRUPT`. Both are wave 2 work (B5, B6).
- A session whose edit panicked is poisoned: `Registry::with` refuses
  further edits and saves with `PANIC` until the document is reopened.
- `save_verified(path, bytes, verify)` writes a unique temp file, fsyncs,
  reads it back and runs the engine's `verify`, copies the previous
  version to the backup folder (`set_backup_dir`), renames and fsyncs the
  folder. `set_backup_dir_c` and `remove_stale_temp_files_c` are
  ready-made bodies for each engine's `<kind>_set_backup_dir` and
  `<kind>_remove_stale_temp_files` exports.
- Hostile-input tests are built inside the Rust tests (no binary fixtures),
  run on a 512 KiB-stack thread where recursion matters, and check time
  and memory where those matter. Keep that pattern for new limits.
- `doc_art`, `doc_cfb`, `doc_image` and `doc_metafile` already have
  `tests/hostile.rs` and `tests/mutate.rs` (xorshift mutation loops),
  built on identical copies of `tests/support/mod.rs` (a xorshift64 `Rng`,
  `mutate`, and `bounded` on a 512 KiB stack). Keep the copies identical
  until B9 replaces them with the planned dev-only `doc_testkit` crate.
  `doc_xml` and `doc_odf` run mutation loops inside their unit tests
  (`src/tests.rs`); `doc_zip`, `doc_opc`, `doc_encoding`, `doc_font`,
  `doc_pdf` and `doc_layout` have none yet.

## Where work stands and what is next

- Wave 1 (B1 shared core and B2 pictures and legacy files) is done and
  verified. What is left reaches here only through the engines:
  - **Wave 2 (B5-B8), partly done.** The text, sheet, word and slide
    engines save through `save_verified` with their own checks and export
    `<kind>_set_backup_dir` (the app sets it); the text engine exports
    `text_remove_stale_temp_files`, which cleans up after every engine.
    Left: reporting too-large parts and XML as `TOO_LARGE` (sheet, and
    word's direct XML errors, do not yet), and a note when
    `Package::duplicate_parts()` is not empty (only the first entry of a
    name is saved). B8 also changes `doc_encoding`
    (lossless round trip: undecodable bytes to private-use code points;
    nine code pages that fail a 256-byte round trip: windows-1253, 1255,
    1257 and 874, ISO-8859-3, -6, -7, -8 and -11).
  - **Wave 3 (B9):** mutation fuzzers for the crates that lack them and a
    shared `doc_testkit` (xorshift mutators, not `cargo-fuzz`, unless the
    owner allows it), run again with `RUST_MIN_STACK=524288`.
- **After release:** a complex-script shaper (GSUB/GPOS) in `doc_layout`
  for Hindi, Telugu and Tamil export; multi-byte East Asian code pages in
  `doc_encoding`.
- The app's `docs/HANDOFF.md` and `PLAN.md` "Next steps" say what to do
  first.
- **2026-10-19 (uncommitted):** `doc_testkit` (mutation helpers, no
  dependencies) and mutation tests in `doc_art`, `doc_cfb`, `doc_image`,
  `doc_metafile` and `doc_opc`; `doc_encoding::encode_lossless` keeps
